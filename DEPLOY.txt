배포 절차
=========

1) Supabase 프로젝트 배포
   PROJECT_REF=<project-ref> \
   ADMIN_PASSWORD='<강한 비밀번호>' \
   SITE_ORIGIN='https://<project>.pages.dev,http://localhost:5173' \
     ./scripts/deploy.sh

   이 스크립트가 link → db push → secrets set → functions deploy →
   스모크 테스트를 순서대로 실행한다. 한 단계라도 실패하면 즉시 멈춘다.
   무엇을 실행할지만 보려면 --dry-run을 붙인다.

   - IP 해시 salt는 db push가 자동 생성하므로 따로 설정하지 않는다.
   - SUPABASE_URL과 SUPABASE_SERVICE_ROLE_KEY는 런타임이 자동 주입한다.
   - supabase link는 DB 비밀번호를 대화형으로 묻는다. 비대화형으로
     실행하려면 SUPABASE_DB_PASSWORD를 환경에 넣어둔다.
   - ANON_KEY를 함께 넘기면 RLS 점검까지 수행한다.
   - 시크릿을 바꾸면 반드시 함수를 다시 배포해야 반영된다. 스크립트를
     다시 실행하면 그 순서가 지켜진다.

   SITE_ORIGIN 닭-달걀: pages.dev 도메인은 Pages를 한 번 배포해야
   생긴다. 최초에는 SITE_ORIGIN='http://localhost:5173'으로 실행하고,
   2)에서 도메인이 생긴 뒤 실제 도메인을 넣어 다시 실행한다. 스크립트가
   멱등하므로 재실행 비용은 없다.

2) Cloudflare Pages 설정
   Cloudflare가 Pages를 Workers로 통합하는 중이라 Create 화면이 Workers로
   먼저 안내한다. Pages 생성 화면으로 직접 가려면:
     Workers & Pages → Create → 상단 "Pages" 탭 → Connect to Git
   탭이 보이지 않으면 아래 URL로 직접 진입한다.
     https://dash.cloudflare.com/?to=/:account/pages/new/provider/github

   저장소: trustspirit/matching, 브랜치: main

   대시보드 입력값
     - Project name: <project>
       *.pages.dev는 Cloudflare 전체에서 유일해야 한다. "matching"은
       이미 다른 사람이 쓰고 있으므로 다른 이름을 골라야 한다.
     - Framework preset: None
       Vite를 고르면 빌드 명령이 npm run build로 바뀌는데, pnpm 워크스페이스
       루트에서는 동작하지 않는다.
     - Build command: pnpm install && pnpm --filter web build
     - Build output directory: apps/web/dist
     - Root directory: 비워둔다(저장소 루트)
     - 환경 변수(Production):
         VITE_API_URL=https://<PROJECT_REF>.supabase.co/functions/v1

   주의
   - Root directory를 apps/web으로 바꾸면 vite.config.ts의 @shared alias가
     해석되지 않아 빌드가 실패한다.
   - VITE_ 변수는 런타임이 아니라 빌드 시점에 번들에 박힌다. 첫 빌드
     전에 넣어야 하고, 값을 바꾸면 재배포해야 반영된다. 없이 빌드되면
     화면에 "사이트 설정이 완료되지 않았습니다."가 뜬다.
   - pnpm 버전은 package.json의 packageManager 필드가 고정한다.
     대시보드에 버전을 지정하지 않는다.
   - SPA 폴백은 apps/web/public/_redirects가 담당한다. 이 파일이 빌드
     산출물 루트로 복사되어 /admin, /result 새로고침을 처리한다.
     Pages 전용 기능이므로 Workers로 옮기면 동작하지 않는다.

3) 배포 후 확인
   - deploy.sh의 스모크 테스트가 게이트웨이 401, CORS, 관리자 비밀번호
     반영, RLS를 자동으로 검사한다. 전부 통과해야 배포가 끝난다.
   - https://<project>.pages.dev/ 접속 → 로그인 화면이 뜬다.
   - https://<project>.pages.dev/admin 접속 → 비밀번호 입력 화면이 뜬다.
   - /admin에서 새로고침해도 404가 아니라 화면이 유지되는지 확인한다.
     (_redirects가 동작하는지 보는 검사다)

4) 실제 데이터 투입
   - 최종 엑셀을 CSV로 저장. 컬럼: 부, 시간, 장소, 조,
     남성 이름/생년월일/연락처/이메일, 여성 이름/생년월일/연락처/이메일
   - /admin 접속 → 비밀번호를 입력해 들어간다. 여기서 쓰는 비밀번호는
     deploy.sh에 넣은 ADMIN_PASSWORD와 같은 값이다. 별도 계정이나 등록
     절차는 없고 관리자는 한 명뿐이다.
   - 한 번 로그인하면 로그아웃하거나 12시간이 지날 때까지 유지된다.
     새로고침해도 다시 입력하지 않는다.
   - 탭이 셋이다. 매칭 / 참가자 / CSV.
     · 처음에는 CSV 탭에서 전체 명단을 올린다.
     · 이후 조 번호나 장소를 고칠 때는 매칭 탭에서 해당 행만 수정한다.
       전체 CSV를 다시 올릴 필요가 없다.
   - 다운로드된 참가자_코드.csv를 안전한 곳에 보관
   - 참가자에게 이름과 코드를 전달

주의
----
- CSV 업로드는 전체 매칭을 대체한다 (증분 추가가 아니다). 이미 등록된
  매칭이 있으면 CSV 탭이 삭제될 건수를 보여주고 확인을 요구한다. 한 건만
  고칠 때는 CSV를 다시 올리지 말고 매칭 탭에서 그 행을 수정한다.
- 참가자 자체는 삭제되지 않으므로 코드는 계속 유효하지만, 매칭이 없는
  참가자는 로그인 시 "등록된 매칭 정보가 없습니다"로 보이게 된다.
- 평문 코드는 업로드 응답에서만 얻을 수 있다. 서버에는 해시만 남는다.
  업로드 성공 화면을 새로고침하면 평문 코드는 영구히 사라진다. 반드시
  다운로드된 CSV를 먼저 보관한 뒤 화면을 떠난다.
- 조를 추가하는 재업로드(전체 매칭 CSV 기준)는 기존 코드를 바꾸지 않는다.
- "전원 코드 재발급"을 켜면 이미 배포한 코드가 전부 무효가 된다.
- 참가자 한 명이 코드를 잃어버렸을 때는 "전원 코드 재발급"을 쓰지 않는다.
  참가자 탭에서 그 사람 행의 "코드 재발급"을 누르면 그 한 명만 새 코드를
  받고 나머지는 그대로다. 새 코드는 누른 직후 화면에만 표시되며 서버에는
  해시만 남는다.
- 참가자를 삭제하면 그 사람의 매칭도 함께 삭제된다. 짝이 된 상대는 짝이
  없어진다. 삭제 전에 화면이 영향 받는 매칭과 짝 이름을 보여주고 확인을
  요구한다.
- 관리자 비밀번호를 15분 안에 10번 틀리면 잠시 차단된다. 15분 뒤 자동으로
  풀린다. 만료된 세션으로 실패하는 것은 이 횟수에 포함되지 않는다.
- 공용 컴퓨터에서 /admin을 썼다면 반드시 로그아웃을 누른다. 세션은 탭을
  닫아도 유지되며 12시간 뒤에 만료된다.
- 사전 리허설 권장: 실제 이벤트 전에 별도 프로젝트에서 실제 엑셀로
  임포트 → 동명이인 1명·2회 참여자 1명 포함 3명 이상 로그인 → 코드 CSV를
  엑셀로 열어 한글이 깨지지 않는지 확인한다.
